## 三、本轮实测新发现的 4 个工程缺陷（此前均未登记）

这些不是推测，是本轮实际跑出来的。

### 3.1 `acceptance.py --reuse` 的 health 判据恒真（**验收层，与 D-38 同型**）

README §5 第 7 条把下面这条列为**主推验收命令**：

```bash
python tools/acceptance.py --reuse runs/r151_shape_baseline.json
```

实测输出（本轮亲跑，93 s）：

```
[PASS] G2 新发 catastrophic=0   0 新发（名单 []，已登记 [37, 50, 51, 91]）
[PASS] G2b degraded 计数（基线 9）  0 <= 9
  health(新): normal 0 / benign 0 / degraded 0 / catastrophic 0
```

**根因**：`r151_shape_baseline.json` 的 86 行里**没有 health 字段**（只有旧的 `crash` 字段），
`shp.summarise()` 读不到 ⇒ `catastrophic_batches=[]`、`degraded_batches=[]`
⇒ **G2 与 G2b 两条 HARD 判据在这种数据上恒真通过**。

这与 R151 关 D-38 时立的纪律（「恒真的判据等于没有判据」）是**同一类错误的复发**，
只是这次发生在 `--reuse` 通路而非引擎通路。

各验收 json 的 health 字段可用性（本轮逐个复算）：

| json | n | n_health | catastrophic | degraded |
|---|---|---|---|---|
| `r151_shape_baseline.json` | 86 | 全 0 | `[]` | `[]` ← **不可用** |
| `r155_acceptance.json` | 86 | 77/0/5/4 | [37,50,51,91] | [40,43,49,54,92] |
| `r156_acceptance.json` | 86 | 77/0/5/4 | [37,50,51,91] | [40,43,49,54,92] |
| `r156_acceptance_v2.json` | 86 | 77/0/9/0 | `[]` | 9 批 |

**修法**：`--reuse` 时若 rows 缺 health 字段 ⇒ G2/G2b 判**跳过并显式告警**（不许报 PASS）；
README 主推命令改为带 health 字段的 `runs/r156_acceptance.json`。

### 3.2 `conservation.py` / `mechanism_cclosure.py` 在 pinned numpy 下**必崩**

requirements.txt 写「numpy 必须 < 2.0，代码用 `np.trapz`，numpy 2.x 已移除该别名」。
实测（numpy 1.26.4）：

```
conservation.element_balance(...)  → AttributeError: module 'numpy' has no attribute 'trapezoid'
mechanism_cclosure.trapz(...)      → AttributeError: module 'numpy' has no attribute 'trapezoid'
```

**陈述与代码相反**：这两个文件用的正是 numpy 2.0 才引入的 `np.trapezoid`。
`conservation_metrics.py` 与 `r138_carbon_observer.py` 用的是 `getattr(np,"trapezoid",None) or np.trapz`（正确写法）；
`test_synthetic_closed_loop.py` 有版本兼容分支（正确）。

**影响**：目前无现役路径 import 这两个模块（grep 全仓无结果）⇒ 是**潜伏**缺陷，不是现役故障。
但它们是"守恒"与"C 平衡自洽"的名义载体，一旦有人按名字调用就崩。
